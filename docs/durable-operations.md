# Durable outgoing operations — M3 contract

Status: specified before implementation. See [application API](application-api.md) for user actions and [background sync](background-sync.md) for transport limits.

An operation has a random stable `OperationId`, version, owner, kind (publication/like/contact), creation/expiry, exact serialized work, target peers, per-item/per-peer confirmed acknowledgements and Pending/Partial/Completed/Failed status. Pending has no adequate acknowledgements; Partial has some but fewer than required; Completed means the configured retention/replica target accepted each required item; Failed is terminal invalid/expired/superseded/blocked work. Completion never means recipient processing. No exactly-once remote delivery is promised.

Commit immutable publication bundles or encrypted parcels before any remote request. Local like intent, parcel insertion and local match notification are one SQLite transaction using the existing FSM. A repeated like returns its existing logical operation, never a newly randomized message. Contact repeats with the same operation id reuse identical bytes. Persist each remote acknowledgement after its response; a crash before persistence retries the exact work safely. Each target counts once. Remote endpoints already enforce signed monotonic profiles, content hashes/leases and parcel ids. Stale/superseded publication work must be terminal rather than republished over a newer revision.

Foreground and scheduled sync flush the same bounded queue through the same finite request/response session plumbing, then use M2 incoming mailbox verification/checkpoints. Budgets cover actual transport bytes, deadlines, contacted peers, item counts, retries and concurrency. A composed service operation cannot silently restart a full budget for every child operation. Cancellation closes temporary transport and leaves unacknowledged work Pending/Partial. Transactions commit only bounded local work and never remain open across network calls. Offline/unreachable peers produce inspectable deferred/partial results and retain pending work. Unknown operation versions, invalid saved credentials/signatures or expiry never cause unauthorized delivery.

Bound serialized records, retained operation count, reports, candidate caches, snapshots and local history. Use explicit StorageFull/InvalidInput outcomes at capacity; do not silently evict uncompleted work. Completed records may be pruned under documented retention while deduplication and terminal FSM history remain authoritative. Database migration is additive and preserves M2 notification acknowledgement and checkpoints.

Local-only content/preferences/contacts remain in private filesystem-protected SQLite, not an encrypted database. Account keys remain exclusively in the encrypted vault. This distinction is a security limitation, not an encryption-at-rest claim.

Failed request checkpoints carry only bounded categories (Unreachable, Rejected, Budget, Cancelled), peer and item identifiers. They stay retryable while the operation is Pending/Partial. A later accepted acknowledgement clears its failed-attempt marker and can never be downgraded by a delayed failure. Receipts count full peers only when every required profile/blob or parcel item has an accepted checkpoint.
